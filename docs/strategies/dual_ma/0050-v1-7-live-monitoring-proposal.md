# 0050 v1.7 正式監控接入提案

> 狀態：**提案，尚未實作、尚未啟用正式通知**
> 適用策略：0050 最終定版 v1.7 之實務成交口徑
> 正式成交定義：訊號日收盤確認，下一個官方交易日開盤成交

## 1. 目標與原則

本提案要把已驗收的 0050 v1.7 回測規則接入既有股票機器人，使用同一個 Bot 程序，但將 ETF 通知送到獨立 Telegram 群組。第一版只做訊號監控與人工下單輔助，不直接串接券商，也不改寫既有 v1.7 回測規則或凍結資料。

核心原則：

1. 線上監控與歷史回測必須使用同一套規則函式與狀態機。
2. 12:45 只作盤中預警；不得把尚未收盤的條件誤稱為 v1.7 正式訊號。
3. 13:55 以完整收盤資料凍結訊號，若成立，指示下一個官方交易日開盤成交。
4. 22:00 完成資料核定；資料更正時必須撤銷或取代舊指令，不得悄悄改寫。
5. 凍結的回測資料保持唯讀；每天只向獨立的線上增量資料區新增正式日線。
6. 每一個正式決策、狀態變化與通知都必須可追溯、可重播及去重。

策略規則仍以 [0050 回測策略規則總表](0050-strategy-rulebook-v1.md) 為準。本文件只定義如何接入正式監控，不重新定義策略。

## 2. 最小上線架構

沿用既有 `main.py`、Telegram Bot、JobQueue 與背景回補服務，只新增四個最小元件：

1. **ETF 監控設定**：獨立群組、ETF 清單、策略版本與排程開關。
2. **v1.7 線上規則計算器**：由已驗收規則抽成可重播的純函式／狀態機，不直接以報告產生器充當線上引擎。
3. **ETF 狀態與事件儲存**：第一版使用 Python 內建 SQLite，不另架資料服務。
4. **三個交易日排程**：12:45、13:55、22:00。

同一個 Telegram Bot token 可以服務不同群組。ETF 路由必須使用明確的 `etf_monitor_chat_id`；設定不存在或錯誤時應停止 ETF 發送並記錄錯誤，不得退回原股票群組，以免誤發。

## 3. 每日監控流程

| 時間 | 階段 | 資料 | 決策定位 | 通知要求 |
|---|---|---|---|---|
| 12:45 | 盤中預警 | 前一日以前正式日線＋今日即時價格／高低點 | 暫估可能進出場，不是正式 v1.7 訊號 | 顯示即時參考價、暫定防守價、條件完成度及「尚未確認」 |
| 13:55 | 收盤正式判定 | 今日正式收盤、高低價＋完整歷史狀態 | 凍結正式訊號；成立時排入下一交易日開盤動作 | 顯示訊號日、訊號收盤價、正式防守價、理由及下一交易日動作 |
| 22:00 | 夜間資料核定 | API 完整日線、公司行動、回補與來源核對結果 | 確認、撤銷或修正 13:55 結論 | 無變更時簡短確認；有變更時完整說明舊／新決策及取代關係 |

所有排程都必須先通過官方交易日曆檢查；非交易日不得產生新的進出場訊號。

### 3.1 12:45 盤中預警

- 使用即時行情作條件預覽，可供使用者提早觀察或準備委託。
- 訊息必須標示「盤中預警／尚未確認」。
- 防守價若納入今日盤中低點，只能標示為暫定值。
- 若使用者依 12:45 訊號實際成交，該行為屬另一個「盤中成交版本」，不能沿用 v1.7 歷史績效；若未來要正式採用，必須另行回測及驗收。

### 3.2 13:55 收盤正式訊號

- 以當日完整日線計算 v1.7 訊號。
- 訊號日不假設能以收盤價成交。
- 正式動作為 `BUY_NEXT_OPEN`、`SELL_NEXT_OPEN` 或 `HOLD`。
- 進出場均使用下一個官方交易日未還原開盤價，不能混用收盤進場與次開出場。
- 使用者可在盤後預掛下一交易日委託，但實際成交價仍應在成交後另行記錄。

### 3.3 22:00 夜間核定

- 完成正式日線、公司行動與資料缺口檢查後，以相同狀態重新判定。
- 結論未變時，發送精簡的「已核定、無變更」通知；可在未來提供靜音設定，但第一版保留每日核定回執。
- 結論改變時，必須發送「資料更正」，具名列出原指令、新指令及是否撤銷待成交動作。
- 不得直接覆寫既有事件；更正要以新事件連結被取代的事件。

## 4. ETF 清單與狀態

ETF 必須與一般股票監控清單分開管理。每檔 ETF 至少保存：

- 代號、名稱、是否啟用。
- 綁定的策略 ID 與策略版本，例如 `0050 / final-v1.7`。
- 使用的正式資料快照及規則版本。
- 最後成功處理的官方交易日。
- 空手、持倉或等待下一交易日成交。
- 進場訊號日、預定／實際成交價與股數。
- 固定初始防守價及分割換算紀錄。
- MACD 出場是否已啟用。
- 最近一次正式決策與通知事件 ID。

第一版只需要以下管理指令：

```text
/etf_list
/etf_add 0050 final-v1.7
/etf_disable 0050
/etf_status 0050
```

第一版採「訊號建議模式」：機器人提供訊號、參考價格與防守價，但不假設已在券商成交。若未來需要追蹤真實損益，再增加人工成交回報，例如：

```text
/etf_fill 0050 buy 203.50 2000
```

## 5. 資料保存與磁碟管理

### 5.1 必須長期保存

- 去重後的正式日線 OHLCV。
- 配息、分割等公司行動。
- 來源、取得時間、資料日期、bytes 與 SHA／receipt。
- 正式進出場訊號、狀態轉換、資料更正及通知結果。
- 使用者回報的實際成交紀錄（若啟用）。

### 5.2 可按保留期清理

- API 的重複原始回應：建議保留 30～90 天。
- 可重建的暫存轉換檔、除錯輸出及重複圖表。
- 一般執行日誌可輪替；含錯誤、訊號或資料更正的相關區段須提升為正式事件後再清理。

### 5.3 不得每天複製整份歷史資料

- 已驗收的 0050 canonical snapshot 保持唯讀。
- 線上資料使用獨立 daily delta；以 `symbol + trading_date` 作唯一鍵更新或去重。
- 線上規則讀取「凍結歷史基底＋已核定增量」，不得直接修改凍結快照。
- 每檔 ETF 每年約 250 筆日線，正式日線本身只占很小空間；磁碟主要風險是重複 raw、研究快取及多份報告，而不是每日新增一筆行情。

## 6. 通知去重與失敗處理

每則事件使用穩定 ID，例如：

```text
symbol + strategy_version + phase + signal_date + decision
```

同一事件重跑時不得重複發送；若第一次發送失敗，可安全重試。通知紀錄至少保存：事件 ID、目標群組、訊息雜湊、嘗試次數、成功時間及 Telegram message ID。

資料不足、來源逾時或狀態檔不一致時採 fail closed：

- 不產生新的正式交易指令。
- 保留既有已核定狀態。
- 向 ETF 群組或維運群組發送「資料不足／暫停判定」，不得把缺資料當成無訊號。

## 7. 通知範本

### 7.1 盤中預警

```text
【0050｜盤中預警｜尚未確認】
時間：2026-10-14 12:45
即時價格：XXX.XX
市場狀態：高市場狀態／低市場狀態
目前判定：可能觸發進場／出場／未觸發
暫定固定防守：XXX.XX
正式判定時間：13:55
```

### 7.2 收盤正式訊號

```text
【0050｜正式進場訊號】
策略：0050 final-v1.7
訊號日期：2026-10-14
訊號收盤價：XXX.XX
執行方式：下一官方交易日開盤進場
正式固定防守：XXX.XX
市場狀態：高市場狀態／低市場狀態
訊號原因：……
資料日期與來源：……
```

### 7.3 夜間核定

```text
【0050｜夜間資料核定】
今日完整資料已補齊。
13:55 正式訊號維持不變。
目前狀態：等待下一交易日開盤進場／持有／空手。
```

## 8. 上線前驗收

短期真實影子監控無法獨立驗證策略，因為 0050 一年可能只有兩三次進場。上線前必須同時完成「完整歷史逐日重播」、「交易事件重播」、「故障情境測試」及「真實影子監控」。

### 8.1 完整歷史逐日重播

正式監控程式必須支援兩種資料／時鐘模式，但共用同一套規則、狀態機與訊息格式：

```text
LIVE
REPLAY
```

`REPLAY` 從 v1.7 已驗收的凍結資料起點開始，一個官方交易日一個官方交易日前進；每一天只能讀到當時已可得資料，依序模擬：

1. 13:55 收盤判定。
2. 22:00 資料核定。
3. 下一交易日開盤成交。
4. 持倉、防守價、MACD 啟用狀態及待成交指令更新。

逐筆及逐日比較：

- 進出場訊號日期。
- 實際成交日期與未還原開盤價。
- 初始防守價及出場原因。
- 股數、費用、交易稅及公司行動。
- 每日現金、持股與總資產。
- 最終損益及績效摘要。

正式通過門檻是零差異；不得用容許誤差掩蓋日期、狀態或成交語意差異。

### 8.2 所有交易事件重播

針對 v1.7 每一筆歷史交易，至少重播進場前五個交易日至出場後兩個交易日，實際產生與未來相同格式的 Telegram 測試訊息，逐一檢查：

- 訊號形成與取消。
- 下一交易日成交。
- 固定防守價。
- MACD 啟用及出場。
- 高／低市場狀態切換。
- 配息、分割及休市銜接。

全期無訊號日只需寫入本機事件檔；所有進出場事件與少量無訊號抽樣才送入測試群組，避免產生數千則無意義通知。

### 8.3 邊界與故障情境

至少驗證：

- MA21 等於 MA144 時歸入高市場狀態。
- 收盤價等於防守價時不誤判嚴格跌破。
- 訊號後遇休市、停牌或無有效開盤價。
- 12:45 可能成立但收盤取消。
- 13:55 與 22:00 資料不一致。
- Telegram 暫時失敗及安全重試。
- 程式在持倉中或有待成交指令時重啟。
- 同一排程重複執行但不重複通知／成交。
- 配息與分割期間的股數、防守價及帳務守恆。

### 8.4 12:45 的歷史驗證限制

只有日線 OHLCV 時，不能精確重建歷史 12:45 的即時價格，也不能拿當日收盤價冒充盤中價格。

- 13:55 正式訊號、22:00 核定及次開成交可以作全期精確重播。
- 12:45 若有可信的歷史分鐘資料才作歷史精確重播。
- 沒有分鐘資料時，以合成邊界案例驗證程式邏輯，再由未來真實影子監控驗證行情與通知流程。

### 8.5 真實影子監控

歷史重播全部通過後，再以測試群組運作 5～10 個交易日，不實際下單。這一階段只驗證：

- 三個排程準時且交易日判定正確。
- 即時行情、正式日線及夜間回補可用。
- Telegram 路由、格式、去重與錯誤重試正常。
- 13:55 與 22:00 的日常結果一致或能正確更正。
- 機器人重啟後可接續原狀態。

由於短期內未必出現交易，影子監控不得取代歷史逐日重播。正式上線後遇到第一個真實交易訊號，仍建議人工覆核一次。

## 9. 驗收報告最低內容

| 項目 | 通過要求 |
|---|---:|
| v1.7 回測交易筆數與監控重播筆數 | 完全相同 |
| 進場訊號／成交日期差異 | 0 |
| 出場訊號／成交日期差異 | 0 |
| 成交價格差異 | 0 |
| 初始防守價差異 | 0 |
| 出場原因差異 | 0 |
| 每日帳務差異 | 0 |
| 未來資料使用 | 0 |
| 重複正式通知／重複成交 | 0 |
| 無法解釋的 13:55／22:00 差異 | 0 |

驗收產物須包含：資料 snapshot ID、規則與程式 commit、設定雜湊、逐筆差異表、逐日帳務比較、事件訊息清冊、測試結果、manifest/SHA/readback 及精確重現命令。

## 10. 建議上線順序

1. 從 v1.7 抽出正式共用規則與狀態機，先證明回測 exact parity。
2. 完成 20 年歷史逐日重播及全部交易事件通知測試。
3. 完成邊界、重啟、去重、資料更正及通知失敗測試。
4. 在 ETF 測試群組執行 5～10 個交易日影子監控。
5. 啟用正式建議模式：12:45 預警、13:55 正式訊號、22:00 核定，由使用者人工下單。
6. 第一個真實交易訊號人工覆核；運作穩定後才考慮實際成交回報、部位損益或增加其他 ETF。

## 11. 第一版不做的事情

- 不串接券商自動下單。
- 不把 12:45 預警當成正式 v1.7 成交。
- 不建立大型資料平台或新的常駐服務。
- 不每天複製完整歷史資料包。
- 不同 ETF 不會因加入清單就自動套用 v1.7；每檔 ETF 必須具名綁定已驗收策略版本。
- 不覆寫、清理或改動既有 0050 v1.7 報告與 canonical snapshot。
